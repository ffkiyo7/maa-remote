# 一图流 / 企鹅物流 数据源调研（实测）

调研时间：2026-09-08 ~15:35–15:45 UTC（= 23:35 CST）。所有结论均为本次 `curl` / `python3` 实测输出，
未使用记忆中的接口。裸 `curl`（默认 UA、无 Referer、无 Cookie、无 token）全部可通。

## 0. 关键发现（先看这个）

1. **一图流没有独立的「活动日历」JSON。** 真正的排期数据在 **`GET https://backend.yituliu.cn/stage/info`**：
   1550 条关卡，每条带 `zoneId / zoneName / stageType / start / end / apCost / spm`，
   `stageType ∈ {MAIN, ACT, ACT_REP, ACT_PERM, ACT_MINI}` —— **`ACT_REP` 就是复刻标记**。
2. **一图流的后端有 OpenAPI 文档**：`https://backend.yituliu.cn/v3/api-docs`（95 KB，200）。
   全站接口一览就在里面，这是本次找到所有接口的权威依据。
3. **物品价值表有真接口**：**`POST https://backend.yituliu.cn/item/v7/value`**，
   `cos.yituliu.cn/arknights/item/value.json` 确实不存在（我另试了 7 条 cos 路径，全 404）。
4. **没有「关卡效率 / 推荐关卡」接口**——前端是在浏览器里现算的。我把它的算法从 bundle 里扒出来并
   **复现验证通过**：用 `item/v7/value` + `matrix.json` + `stage/info` 重算，
   **1-7 的效率恰好 = 1.000**（一图流的价值表就是以「每种材料的最优关效率 = 1」归一化的），说明口径吻合。
5. **复刻间隔可统计**：`stage/info` 里 42 组 `ACT → ACT_REP` 配对，
   **中位数 378 天**，近两年样本集中在 345–410 天。这是「复刻时间预估」权重最靠谱的经验基准。
6. **许可**：一图流 = CC BY-NC 4.0 + 强制署名；企鹅物流数据 = CC BY-NC 4.0（官方文档原文，见 §7）。

## 1. 关卡 / 活动排期：`GET https://backend.yituliu.cn/stage/info`

### 请求与响应头

```
$ curl -sS -D - https://backend.yituliu.cn/stage/info
HTTP/1.1 200
Server: nginx/1.18.0 (Ubuntu)
Content-Type: application/json
Transfer-Encoding: chunked
Vary: Origin, Access-Control-Request-Method, Access-Control-Request-Headers
（size 313585 字节）
```

- **没有** `Cache-Control` / `Last-Modified` / `ETag` —— 需要自己在本地控制刷新频率
  （前端自己在 IndexedDB 里缓存 1 小时，key `stageInfo-v4`）。
- CORS：`Access-Control-Allow-Origin: *`（带 `Origin: https://example.com` 实测返回）。
- 裸 `curl -A ''` 也返回 200 —— **无 UA / Referer / token 要求**。
- OpenAPI 里 summary 为「获取关卡信息」，tag `材料相关API-v7`。

### 字段说明

响应外层是一图流统一包 `{"code":200,"msg":"操作成功","data":[...]}`。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `stageId` | string | 关卡内部 id，**与 MAA `stages.json` / 企鹅 `matrix.json` 同一套 id**。活动复刻加 `_rep` 后缀，常驻（别传/插曲）加 `_perm` |
| `stageCode` | string | 显示关号，如 `SR-8` / `1-7` / `GT-1` |
| `zoneId` | string | 章节 / 活动 id，如 `act54side_zone1` |
| `zoneName` | string | 章节 / 活动名。**注意：当期新活动的 zoneName 是占位符 `新活动关卡`**，事后才改成正式名 |
| `stageType` / `type` | string | 两个字段值完全一致。`MAIN`(396) / `ACT`(472) / `ACT_REP`(366) / `ACT_PERM`(158) / `ACT_MINI`(158) |
| `start` | int64 | 开放时间，**Unix 毫秒**（UTC 纪元）。渲染要用 `Asia/Shanghai`，边界都落在 16:00 或 04:00 CST |
| `end` | int64 | 关闭时间，Unix 毫秒。**永不为 null**；常驻/主线用哨兵值 `4070880000000`（2098-12-31 16:00 CST） |
| `apCost` | int | 理智消耗 |
| `spm` | float | **= apCost ÷ 最短通关分钟数**（理智/分钟）。实测与企鹅 `minClearTime` 完全对齐，见下 |

`spm` 语义实测（`apCost / spm` vs 企鹅 `stages` 的 `minClearTime`）：

```
a001_01 GT-1 ap 9  spm 3.88 -> 2.32 min   企鹅 minClearTime 2.32 min
a001_04 GT-4 ap 12 spm 4.34 -> 2.76 min   企鹅 minClearTime 2.77 min
```

## 2. 物品价值表：`POST https://backend.yituliu.cn/item/v7/value`

`https://cos.yituliu.cn/arknights/item/value.json` 实测 **404**（另外 `arknights/item.json`、
`arknights/activity.json`、`arknights/stage/info.json`、`arknights/stage-drop/item.json` 等 7 条也全 404；
COS 桶不允许 list：`?list-type=2` 返回 `AccessDenied`）。真实路径是后端的 POST 接口。

### 请求

```
$ curl -sS -X POST https://backend.yituliu.cn/item/v7/value \
       -H 'Content-Type: application/json' -d '{}'
HTTP/1.1 200   Content-Type: application/json   size=22342
→ {"code":200,"msg":"操作成功","data":[ 129 条 ]}
```

- **空 body `{}` 就能拿到默认口径的价值表**（129 条）。无鉴权、无 UA/Referer 要求。
- 响应头**没有** `Cache-Control` / `Last-Modified` / `ETag`。
- 可传 `ItemValueConfigDTO` 自定义口径（字段见 `/v3/api-docs` 的 `ItemValueConfigDTO`）。
  **坑（实测踩到）**：`chipPreference` 的 key 必须是**小写开头**的
  `tank_MEDIC / sniper_CASTER / pioneer_SUPPORT / warrior_SPECIAL`；
  用前端 JS 里的 `TANK_MEDIC` 大写写法会 500：
  `Cannot invoke "String.hashCode()" because "<local3>" is null`。
- 前端（ark.yituliu.cn）**其实不调这个接口**，它把整套算法搬到浏览器里现算，
  bundle 里还内嵌了一份默认价值表快照（变量 `PSe`）。两边数值一致
  （如 30145 晶体电子单元 `itemValueAp` 均为 `325.96250672267115`）。

### 字段说明（`ItemInfoDTO`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `itemId` | string | 与 MAA `item_index.json` 同一套 id |
| `itemName` | string | 中文名 |
| `itemValue` | double\|**null** | 物品价值（理智当量）。**16 条为 null**（活动代币、理智小样、补给箱等），必须判空 |
| `itemValueAp` | double\|null | 等效理智值（与 `itemValue` 极接近，差在龙门币折算口径） |
| `rarity` | int | 1–5 |
| `weight` | double | 归一化用的权重，多数为 0 |
| `cardNum` / `groupId` | int | 前端分组展示用 |
| `type` | string | `精英材料`(60) / `芯片`(24) / `抽卡道具`(7) / `作战记录`(4) / `技能书`(3) / `龙门币`(1) / `""`(30) |

## 3. 关卡效率 / 推荐关卡：**没有独立接口，需自算**（算法已复现验证）

`/v3/api-docs` 里**没有**任何 stage-efficiency / recommendation 端点。
前端 `main-BQ0POL0x.js` 里的实现（函数 `GM` / `xEe`）是纯客户端计算，数据只来自三处：

```js
// 一图流前端的真实数据源（从 bundle 抠出）
getPenguinMatrixCache: () => axios.get("https://cos.yituliu.cn/arknights/stage-drop/matrix.json")  // 缓存 1h
getStageInfoCache:     () => request({url:"/stage/info", method:"get"})                            // 缓存 1h
getItemValueCacheByConfig: 本地迭代 50 轮算出物品价值（等价于 POST /item/v7/value）
```

### 它的公式（逐行读 bundle 得到）

```
每次通关期望产出  E(stage) = Σ_item ( quantity/times × itemValue[item] )
                          + apCost × 12 × itemValue["4001"]          // 每点理智 12 龙门币
                          + [仅 ACT/ACT_REP] apCost/price × quantity × itemValue[活动商店最优兑换物]
关卡效率 stageEfficiency = E(stage) / apCost
```

前端展示口径附注（bundle 内原文，直接引用）：

> 只有多于300样本的关卡才会被收录。仅收录由自动刷图软件上报的掉落数据。活动关卡只在活动期间出现。
> 插曲和别传常驻后重新计算效率，该效率与活动时无关。

前端默认配置 `sampleSize: 300`、`source: "penguin"`、`useActivityStage: false`。

### 我的复现验证

用 `item/v7/value`(`{}`) + `matrix.json` + `stage/info`，只取当前开放关卡（534 关）：

```
1-7  (main_01-07)  eff = 1.000    ← 归一化基准点，完全对上
14-17(main_14-15)  eff = 2.012    主产 酮凝集组
14-20(main_14-18)  eff = 1.985
```

`1-7 == 1.000` 说明一图流的价值表就是按「每种材料的最优关效率 = 1」迭代归一化的，我的重算口径与它一致。

单材料最优关（`异铁组 30043`，当前开放关）：

```
SR-8  act54side_08  0.03702 件/理智 → 27.02 理智/件 (times=1590021, ACT)
14-12 main_14-11    0.02477 件/理智 → 40.37 理智/件 (times=358998,  MAIN)
10-11 tough_10-10   0.01904 件/理智 → 52.53 理智/件
```

活动关 SR-8 比最优主线关便宜 **33%** —— 这正是「活动期优先刷」信号的量化来源。

## 5. 掉落矩阵：`https://cos.yituliu.cn/arknights/stage-drop/matrix.json`（复核）

```
HTTP/1.1 200   Content-Type: application/json
Cache-Control: max-age=7200
Access-Control-Allow-Origin: *
ETag: "92f26b407eb9adcea60b89727aa1d0ad"
Last-Modified: Tue, 08 Sep 2026 15:40:03 GMT   Content-Length: 1395165
```

- **`Cache-Control: max-age=7200` 是骗人的**：我 15:34 和 15:40 两次请求，`Last-Modified` 从
  `15:30:05` 变成 `15:40:03`，**实际约 10 分钟刷一次**。要拿新数据请用 `ETag` / `If-Modified-Since`，
  别信 max-age。
- 结构 `{"matrix":[{stageId,itemId,times,quantity,stdDev,start,end}]}`，**10975 行**，144 个 itemId，1439 个 stageId。
- `end == null` 的有 **6172 行 = 该统计区间仍在累积（进行中）**；`start` 永不为 null。
- 与企鹅 `show_closed_zones=true`（12491 行）比：**镜像是严格子集**（yituliu-only = 0 行），
  少的 1516 行偏低样本（被丢行 `times` 中位数 234，保留行中位数 21471），另外整类丢掉了
  `4001_1000/1500/2000/10000` 这 4 个龙门币包伪物品。具体裁剪规则没找到成文依据。
- 与企鹅**实时**（`show_closed_zones=false`，8085 行）比：共有 7147 个 (stage,item) 键，
  其中 422 个数值完全相同、6725 个略有差异 —— 就是**快照时刻差**（例：`act11d0_02_perm/30051`
  镜像 times=510 vs 实时 517）。镜像滞后 ≲10 分钟，可接受。

## 6. 企鹅物流元数据（一图流的后备）

```
X-Penguin-Compatible: frontend-v2@v3.4.0
```

| 接口 | 大小 | 条数 |
| --- | --- | --- |
| `https://penguin-stats.io/PenguinStats/api/v2/zones` | 113775 B | 167 |
| `https://penguin-stats.io/PenguinStats/api/v2/stages` | 1319419 B | 1612 |

### 6a. `/zones` —— **含活动开放/结束时间与复刻**

字段：`zoneId, zoneIndex, type, subType, zoneName, zoneName_i18n, existence, background, stages[]`

- `type` 分布：`ACTIVITY`(117) / `MAINLINE`(23) / `ACTIVITY_PERMANENT`(19) / `WEEKLY`(6) / `GACHABOX`(1) / `RECRUIT`(1)。
- `existence.CN = {exist, openTime, closeTime}`，Unix 毫秒。**`closeTime` 为 `null` 表示常驻/无限期**（50 个 zone 如此）
  —— 这点和一图流用 `4070880000000` 哨兵值不同，处理逻辑要分开写。
- **复刻**：`zoneName` 带 `·复刻`，`stages[]` 里的 id 带 `_rep`。**没有 `subType` 标记**（实测 `subType: null`）。
- **含正式活动名**（比一图流 `stage/info` 的占位符准），也**含 `stages[]` 数组**（一图流是靠 zoneId 反查）。
- **不含未来预告**：最大 `zoneIndex` 就是当期活动，没有「下次复刻是什么」的前瞻数据。

样例 2 条：

```json
{"zoneId":"act44sre_zone1","zoneIndex":1116,"type":"ACTIVITY","subType":null,
 "zoneName":"墟・复刻","zoneName_i18n":{"en":"Ato - Rerun","zh":"墟・复刻"},
 "existence":{"CN":{"exist":true,"openTime":1787342400000,"closeTime":1788206400000},
              "JP":{"exist":false},"KR":{"exist":false},"US":{"exist":false}},
 "background":null,
 "stages":["act44side_01_rep","act44side_02_rep","...","act44side_08_rep"]}

{"zoneId":"act54side_zone1","zoneIndex":1117,"type":"ACTIVITY","subType":null,
 "zoneName":"月行水上",
 "existence":{"CN":{"exist":true,"openTime":1788494400000,"closeTime":1789675200000}},
 "stages":["act54side_01","...","act54side_08"]}
```

### 6b. `/stages` —— **含掉落表（定性）与最短通关时长**

字段：`stageId, zoneId, stageType, code, code_i18n, apCost, existence, minClearTime, dropInfos[]`

- `dropInfos[] = {itemId, dropType, bounds:{lower,upper}}`，
  `dropType ∈ NORMAL_DROP / EXTRA_DROP / SPECIAL_DROP / FURNITURE`。**只有定性掉落表，没有掉率**（掉率在 matrix）。
- `minClearTime` 毫秒；`apCost / (minClearTime/60000)` == 一图流的 `spm`（实测吻合到小数点后 2 位）。
- `existence` 只有 `{exist:bool}`，**没有 openTime/closeTime**（时间在 `/zones`）。

样例 1 条（`dropInfos` 截断）：

```json
{"stageId":"main_01-07","zoneId":"main_1","stageType":"MAIN","code":"1-7",
 "apCost":6,"existence":{"CN":{"exist":true},"JP":{"exist":true}},
 "minClearTime":118000,
 "dropInfos":[{"itemId":"30012","dropType":"NORMAL_DROP","bounds":{"lower":1,"upper":2}},
              {"itemId":"30011","dropType":"EXTRA_DROP","bounds":{"lower":0,"upper":1}}]}
```

### 6c. `/items`

字段：`itemId, name, name_i18n, itemType, sortId, rarity, groupID, spriteCoord, alias, pron, existence`

- `itemType ∈ MATERIAL / CARD_EXP / ...`；`rarity` 是 **0-based**（固源岩组 rarity=2，一图流同物品 rarity=3）——
  **两边稀有度差 1，join 时别混用**。
- `alias.zh` 带俗名（固源岩组 → `土块` / `石头`），对 Discord 里用户口语输入的匹配有用。

样例 1 条：

```json
{"itemId":"30013","name":"固源岩组","name_i18n":{"en":"Orirock Cluster","zh":"固源岩组"},
 "itemType":"MATERIAL","sortId":100013,"rarity":2,"groupID":"orirock",
 "spriteCoord":[0,1],"alias":{"zh":["固源岩组","土块","石头"]},
 "existence":{"CN":{"exist":true}}}
```

## 8. 建议：三个加权项各用什么

### ① 平均用量 / 复刻时间预估（越久越优先）

**数据源**：`GET https://backend.yituliu.cn/stage/info`（唯一必需），配 `matrix.json` 拿掉落。

**计算口径**：

1. 把 `stageType=="ACT"` 的 zone 与 `stageType=="ACT_REP"` 的 zone 用 `stageId` 去尾（`_rep`）配对，
   得到每个活动的首发日与复刻日。
2. 对当前**未复刻**的活动，`预计复刻时间 = 首发 start + 378 天`（近 3 年样本中位数；p25–p75 = 351–387 天，
   建议用 ±20 天作为不确定带）。
3. 对某材料 `i`：找出**当前正在开放**且掉 `i` 的关（`start <= now <= end`），
   若最优关是 `ACT`/`ACT_REP` 且 `end - now` 很短 → 紧迫度高；
   若该材料在活动关外没有像样的关（`最优常驻关理智/件 ÷ 最优活动关理智/件 > 1.3`）→ 加权更高。
4. 「离下次能刷到还有多久」= `min(下一次已知开放窗口, 预计复刻时间) - now`，越大权重越高。

**注意**：`stage/info` 的 `end` **永不为 null**，常驻用哨兵 `4070880000000`；判「是否常驻」用
`end > now + 10年` 或直接看 `stageType ∈ {MAIN, ACT_PERM}`，别判 null。
当期新活动 `zoneName` 是 `新活动关卡` 占位符，要显示活动名请用 `/item/v5/store/activity` 的 `actName`
或企鹅 `/zones` 的 `zoneName`。

### ② 仓库现缺口

**数据源**：项目里已有的森空岛仓库快照（`scripts/maa_depot.py` 走 MAA `item_index.json`）
+ **`POST https://backend.yituliu.cn/item/v7/value`**（`{}` 即可）做「缺口 → 理智当量」的换算。

**计算口径**：`缺口价值(i) = 缺口件数(i) × itemValue(i)`。
把不同稀有度的缺口拉到同一个「理智」量纲上再排序，比按件数排序合理得多
（1 个晶体电子单元 = 302 理智 ≈ 17.6 个固源岩组）。

**注意**：129 条里 **16 条 `itemValue == null`**（活动代币等），必须判空跳过。
一图流 rarity 与企鹅 rarity **差 1**，用 MAA `item_index.json` 做 id→中文名的唯一权威。

### ③ 掉落效率

**数据源**：`https://cos.yituliu.cn/arknights/stage-drop/matrix.json`（主）
+ `GET /stage/info`（apCost / 开放窗口 / spm）+ `POST /item/v7/value`（物品价值）。

**两种口径，按用途选**：

- **单材料口径（推荐给「刷这个材料去哪」）**：
  `理智/件 = apCost ÷ (quantity / times)`，取当前开放关里最小的。
  实测例：异铁组 → SR-8 27.02 理智/件 vs 主线最优 14-12 40.37 理智/件。
- **综合关卡效率（推荐给「这关值不值得刷」）**：
  用 §3 那条前端公式，含 `apCost × 12 × value(4001)` 龙门币项；
  实测 1-7 == 1.000，可直接拿 1.0 当及格线。

**注意**：
- 样本阈值照抄一图流：`times >= 300` 才计入（前端默认 `sampleSize: 300`）。
- `end == null` = 区间仍在累积；同一 (stageId,itemId) 在 matrix 里**不会重复**（实测 dup=0），可直接建字典。
- `matrix.json` 实际 ~10 分钟更新一次，`Cache-Control: max-age=7200` 不可信，用 `ETag`。
- 想要绝对最新/最全（含被镜像裁掉的 1516 行低样本），直接打企鹅
  `/api/v2/result/matrix?server=CN&show_closed_zones=true`（12491 行，1.59 MB，`max-age=300`）。
- **加个时间成本项可选**：`stage/info.spm` 给了「理智/分钟」，
  刷同样理智，`spm` 越大挂机墙上时间越短。当期 SR-8 `spm=74.12`（21 理智约 17 秒），
  SR-2 `spm=5.35`（9 理智约 101 秒），差 14 倍，对自动化排队很有意义。

### 未找到 / 不确定的项

1. **「预计复刻时间」官方值：不存在。** 一图流、企鹅都没有前瞻排期接口。
   bundle 里唯一的「未来活动」列表（`ETTe`）是**攒抽计算器**用的两条硬编码卡池排期
   （`P3R联动 2026-09-04~09-17`、`感谢庆典 2026-11-01~11-14`，带 `accuracyFlag:false` 并在 UI 上明写
   「无准确排期，默认给出可能性最大的排期」），**与材料无关，不要拿来当材料复刻预估**。
2. **一图流没有「关卡效率 / 推荐关卡」接口**，只能按 §3 自算。好在算法已完整复现且用 1-7==1.000 验过。
3. **`matrix.json` 相对企鹅少 1516 行的裁剪规则**没找到成文依据，只观察到偏低样本
   （被丢行 times 中位数 234 vs 保留 21471）。若在意完整性就直接用企鹅原始接口。
4. **周常关（`wk_*`）与 EX 关不在 `/stage/info` 里**，理智与掉落要回落到 MAA `stages.json`
   （周常有，如 `wk_armor_3` SK-3 ap=20）和你们现有的 EX OCR 方案。
5. **`/item/v5/custom` 在 bundle 里被调用但服务端 404**（`{"status":404,"path":"/item/v5/custom"}`），
   属于前端残留死代码，别依赖。
6. **一图流后端无缓存头**（`/stage/info`、`/item/v7/value` 都没有 `Cache-Control`/`ETag`），
   自己做本地缓存；照抄前端的 1 小时 TTL 是合理起点。
